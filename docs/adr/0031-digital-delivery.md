# 0031 Digital delivery

Status: accepted (task 2.10)

- **Entities** (`schema/digital.ts`): `DigitalAsset` (filename, private `storageKey`, type, size) and `DownloadGrant` (order line + asset, `maxDownloads`, `downloads`, `expiresAt`, `revokedAt`, `accessHash`). A digital `Variant` points at its asset with the optional `digitalAssetId`. The asset is referenced by id, not copied, so **replacing a file updates the asset in place and every grant stays valid** (counts kept; later downloads get the new file; the old object is deleted afterwards, best effort).
- **Only reachable through a grant.** `createDownloads.url` checks the caller's proof, then returns a signed URL that lives 60 s. Storage keys never appear in a response (admin views strip them). The serving route already sends `nosniff` and `attachment`; `StorageProvider.signedUrl` gained an optional `{ filename }` so S3 URLs carry `response-content-disposition: attachment; filename*=…` (the local adapter ignores the name and always serves an attachment).
- **Counting:** a download is counted when a URL is issued, atomically (`DownloadGrantRepository.consume`, one conditional UPDATE in Postgres, the shared pure rule `decideConsume`). The URL is signed first, so a storage failure never burns a download. The 60 s URL can in principle be fetched more than once; the limit bounds URLs issued, which is what a store can enforce without proxying the bytes.
- **Who may download (IDOR):** a customer session opens the grants of the orders `customerOrders` returns for them; a guest presents a link token in the `x-download-token` header (never in a URL). A grant the proof does not open is `not_found`, identical to a non-existent id. Spent states (`revoked`, `expired`, `exhausted`) are only revealed to someone who is allowed to see the grant (403 with a `reason`).
- **Guest link:** `issueLink(orderId)` makes a 256-bit random `dl_…` token, stores only its SHA-256 on the order's grants and returns the token once, for the delivery email (task 2.0 calls it from the `order.paid` handler). Issuing again replaces the hash, so older emails stop working. Links die with the grants (expiry, revocation).
- **Wiring:** `downloads.grant(tx, order)` is the checkout's `grantDownloads` (one grant per digital line whose variant has an asset; idempotent by a grant id derived from the line id; a digital variant with no asset gets no grant rather than failing a paid order). `downloads.revoke(tx, order)` is the refund service's `revokeDownloads`; the testkit proves a refund revokes through it.
- **Settings:** `lifetimeDays` (default 30) and `maxDownloads` (default 5), `null` = unlimited, are `createDownloads` options applied to new grants. There is no persisted settings store yet; it arrives with the settings screens and only replaces where these two values come from. URL lifetime is fixed (60 s), not a setting.
- **Storage:** documents in `assets` and `grants` (migration module `downloads`); grants are indexed by order and by link hash.
- **Admin routes:** `POST /admin/digital-assets?filename=` (upload + register), `PUT /admin/digital-assets/:id?filename=` (replace), list and get. The old key-based `DELETE /admin/digital-assets` is removed: deleting a file out from under sold grants is not supported in v0.1 (replace instead).
- **Store routes:** `GET /store/downloads`, `POST /store/downloads/:id/url` (response marked sensitive: never stored for idempotent replay).
- **Not here:** the delivery email (2.0), customer-initiated link resend, and composing `grant`/`revoke` into the app's checkout and refund services (no composition root exists yet; both are plain function values).
